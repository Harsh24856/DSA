Deep dive · 3.7 context engineering, drawn

Budgeting the context window and caching the prefix

Every call has a fixed window shared by instructions, tools, documents, history and the answer. Context engineering is deciding what earns a place, in what order, and what can be cached.

Rules of thumb

  • Reserve the output budget first; a response cut off at max tokens is a common silent failure.
  • Cap retrieved text (for example 50 to 60% of the budget) and keep only the best-ranked chunks.
  • Drop or summarise the oldest turns, never the system prompt or the question.
  • Put anything that varies per user (timestamps, names) after the cached prefix, or the cache never hits.

Why order matters

  • Models recall the start and end of long contexts better than the middle, so put the question and key instructions last.
  • Label sections with tags (<docs>, <question>) so the model can tell instructions from data, which also helps against injection.

Check yourself

  1. Your prompt cache hit rate is near zero. What is the usual cause?

    Something early in the prompt changes on every call: a timestamp, the user's name, a shuffled tool list or retrieved documents placed before the stable instructions. Caching matches an exact prefix, so move every per-request value after the cache breakpoint.

  2. The model ignores an instruction buried in a 50-page context. What do you change?

    Move the instruction to the end, next to the question, repeat the critical constraint there, cut irrelevant context (better retrieval or summaries), and mark sections with clear tags. Long windows do not guarantee the model attends to everything equally.

  3. History is filling the window in a long chat. Options?

    Keep a sliding window of recent turns, summarise older turns into a running memory note, store facts in long-term memory and retrieve them when relevant, and trim tool outputs to the fields the model needs.

Deep dive · 3.8 structured output that never breaks your parser

From "please return JSON" to guaranteed shapes

Three levels of reliability

  1. Ask nicely with an example: often works, sometimes adds chatter or wrong types.
  2. Validate and retry: parse with a schema (Pydantic, Zod); on failure send the exact error back and ask for a fix.
  3. Constrained decoding (structured outputs / tool schemas): at each step the server masks tokens that would break the JSON schema, so the output always parses. You still validate business rules.

Check yourself

  1. Constrained decoding guarantees valid JSON. Why validate anyway?

    The schema guarantees shape, not truth. A total can be negative, a date can be in the future, an id can point to nothing. Business rules, cross-field checks and hallucinated values still need validation and sometimes a retry.

  2. Function calling vs structured outputs: what is the difference?

    Function calling lets the model choose to call one of your tools and produce arguments matching that tool's schema; your code runs it. Structured output forces the final answer itself into a schema. Under the hood both rely on the model being trained (and often constrained) to emit schema-valid JSON.

  3. How do you measure an extraction pipeline?

    A labelled test set of documents with expected fields; report field-level accuracy, the rate of invalid outputs before and after retries, retries per document, latency and cost. Track it in CI so prompt changes cannot silently regress.

Check yourself

  1. Users complain answers are wrong. Retrieval recall@5 is 0.95. Where do you look?

    Retrieval is fine, so check generation: is the context too long or badly ordered, does the prompt demand citations and "say you do not know", is the model ignoring a contradicting chunk, are chunks missing surrounding context. Measure faithfulness and correctness on the failing cases.

  2. Why use RRF instead of adding BM25 and cosine scores?

    The scores live on different scales (BM25 is unbounded, cosine sits in [-1, 1]) and shift with the corpus. RRF uses only ranks, 1/(k + rank), so it needs no calibration and one strong list cannot drown the other.

  3. How do you build a retrieval eval set quickly?

    Sample real user questions (or generate questions from chunks with an LLM), label which chunks answer each, spot-check the labels, and keep 50 to 200 examples. Rerun recall@k and MRR on every change to chunking, embeddings or ranking.

Deep dive · 6.6 the memory math behind fine-tuning

Why LoRA fits on one GPU and full fine-tuning does not

Per trained parameterBytes

bf16 gradient2
Adam moments m and v (fp32)8

Full fine-tuning pays 16 bytes for every one of 7 billion parameters. LoRA pays 16 bytes only for the small adapters and 2 bytes (bf16) or 0.5 bytes (4-bit, QLoRA) for the frozen base.

Check yourself

  1. Why is the optimizer state bigger than the model?

    Adam keeps two running averages per parameter (momentum and squared gradients), usually in fp32: 8 bytes, versus 2 bytes for a bf16 weight. With a fp32 master copy and gradients, training costs about 16 bytes per parameter before activations.

  2. QLoRA quantizes the base model to 4 bits. Does that hurt the fine-tuned quality?

    Usually only a little: the adapters are trained in higher precision on top of the frozen 4-bit weights (NF4 with double quantization), and they learn to compensate. The bigger risk is task data quality, not the quantization.

  3. When is DPO not enough?

    When you can check answers automatically (math, code, tool tasks), online RL with verifiable rewards (for example GRPO) can keep improving from the model's own samples, while DPO only learns from a fixed set of preference pairs.

Check yourself

  1. What can go wrong with a semantic cache?

    Two questions can be similar but need different answers ("refund policy in the EU" vs "in the US"), or the cached answer goes stale, or one user's personal answer leaks to another. Use a strict similarity threshold, include the user or tenant and key parameters in the cache key, and set expiry.

  2. Why does continuous batching cut average latency so much?

    In static batching a 30-token request waits for the 420-token request in its batch. Continuous batching lets it finish and leave after 30 steps, and its slot is immediately reused by the next request in the queue.

Turning pixels and sound into tokens

Check yourself

  1. Your vision feature is expensive. What is the first fix?

    Resize images to the smallest resolution that still answers the question: token count grows with area, so halving width and height cuts tokens about 4×. Crop to the relevant region, and send text (OCR) instead of images when the content is just text.

  2. Why do vision models tile large images?

    The encoder was trained at a fixed resolution. Tiling keeps fine detail (small text in a screenshot) by encoding several full-resolution crops plus a downscaled overview for global layout, at the cost of more tokens.

  3. Speech-to-speech vs a speech-to-text, LLM, text-to-speech chain?

    The chain is easier to build, debug and swap parts in, but each hop adds latency and loses tone. A native speech-to-speech model responds faster and can keep emotion and interruptions, but is harder to control and evaluate.

Questions interviewers ask about your project

  1. Why did you choose that chunk size?

    Answer with evidence: "I tried 256, 512 and 1,024 tokens with 15% overlap and measured recall@5 on my 100-question set; 512 scored best because our answers usually span a paragraph." An answer backed by an experiment beats a rule of thumb.

  2. How do you know the answers are correct?

    A labelled eval set run in CI: recall@k for retrieval, an LLM judge for faithfulness checked against human labels on a sample, and correctness against reference answers. Plus user feedback logged with each trace.

  3. What breaks first at 100× the traffic?

    Usually cost and rate limits on the LLM API, then the vector store's memory and the reranker's latency. Mitigations: caching, routing to a smaller model, batching rerank calls, sharding or quantizing the index, and queueing ingestion.

  1. The cost estimate is over budget. Which levers do you pull, in order?

Worked design · 2 an LLM gateway for a whole company

One front door for every team's model calls

Why build it

  • Provider keys stay in one place; teams never see them.
  • Per-team budgets and rate limits stop one runaway job draining the account.
  • Fallback across providers keeps apps up during an outage.
  • One audit log for data-protection reviews.

Hard parts

  • Streaming through the gateway without adding latency.
  • Normalising different providers' request and tool-call formats.
  • Cache keys that respect tenant boundaries.
  • Counting tokens consistently for billing.

Check yourself

  1. Provider 1 starts returning 429s. What should the gateway do?

    Respect Retry-After with jittered backoff for retriable requests, shift traffic to a fallback provider or model if the request allows it, shed low-priority batch traffic first, and alert. Never retry indefinitely on user-facing requests: fail fast with a clear message.

  2. How would you prevent one team's cached answers leaking to another?

    Include the tenant id (and any user-level scope) in every cache key, never share semantic-cache entries across tenants, and exclude responses containing personal data from caching.

Worked design · 3 an internal agent platform

Agents that act on company systems, safely

Check yourself

  1. Why should the agent act with the user's permissions, not a service account?

    So it can never do more than the person asking could do themselves. A shared admin account turns any successful prompt injection into an admin action; per-user credentials limit the damage and keep the audit trail honest.

  2. How do you evaluate an agent before giving it to the whole company?

    Scripted tasks with known end states (was the ticket created with the right fields), measured on success rate, steps, cost and safety violations; replay real traces in a sandbox; red-team with injected documents; then a staged rollout with approvals switched on.

Model answers · say it in 60 seconds

Eight answers worth rehearsing out loud

Structure each answer as: one-line definition, how it works, one trade-off, one example from your own work.

  1. Walk me through how RAG works and where it fails.

    RAG retrieves relevant chunks from your documents and puts them in the prompt so the model answers from them with citations. Offline: parse, chunk, embed, index. Online: retrieve with hybrid search, rerank, generate. It fails at parsing, retrieval (measured by recall@k), ranking, or generation (faithfulness), so I debug by checking each stage on failing questions.

  2. Explain attention and why it is O(n²).

    Each token makes a query, key and value. A token's query is compared with every key, softmax turns the scores into weights, and the output is the weighted sum of values. Every pair of tokens gets a score, so n tokens need n² scores; FlashAttention computes them in tiles to avoid storing the n × n matrix, but the compute is still quadratic.

  3. Prompting vs RAG vs fine-tuning: how do you choose?

    Start with prompting. Add RAG when the model lacks knowledge or the knowledge changes. Fine-tune when you need a consistent behaviour, format or style the prompt cannot reliably produce, or to make a small model do one task cheaply. Knowledge goes in retrieval; behaviour goes in weights.

  4. What is the KV cache and why does it matter for serving?

    During generation each new token needs the keys and values of all earlier tokens; the KV cache stores them so they are not recomputed. It makes decoding fast but grows with context length times concurrent users, so it, not the weights, often limits how many users a GPU can serve. GQA, paging and quantization shrink it.

  5. How do you evaluate an LLM application?

    A versioned test set of real inputs with expected outputs or rubrics; automatic metrics where possible (exact match, schema validity, recall@k), an LLM judge calibrated against human labels for open-ended quality, and online signals (feedback, escalations). Run it in CI so every prompt or model change shows its effect.

  6. What is an agent, and when should you not build one?

    An LLM in a loop that chooses tools until a goal is met. Do not build one when the steps are known in advance: a fixed workflow is cheaper, faster and easier to test. Use an agent when the path genuinely depends on intermediate results, and add step caps, approvals and evals.

  7. How does LoRA work and why is it so cheap?

    LoRA freezes the original weights and learns a low-rank update B·A beside each targeted matrix. With rank 16 on a 4096 × 4096 layer that is 131k trainable numbers instead of 16.8 million, so gradients and optimizer state are tiny; QLoRA also stores the frozen base in 4 bits, so a 7B model fits on one consumer GPU.

  8. How do you defend against prompt injection?

    Assume it will sometimes succeed and limit the damage: least-privilege tools acting with the user's permissions, untrusted text clearly marked as data, human approval for irreversible actions, output validation and allow-listed destinations, and monitoring of tool calls. Prompt wording alone is not a defence.
