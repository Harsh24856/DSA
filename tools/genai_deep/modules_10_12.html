Building the first set

  • Start with 30 to 100 real inputs, not invented ones; include the cases users complained about.
  • Write what "good" means per item: a reference answer, required facts, or a rubric.
  • Tag items (easy, hard, adversarial, by feature) so you can see where a change helps or hurts.
  • Freeze a version; never tune on the items you report.

Offline vs online

  • Offline: run the fixed set on every change, in CI. Fast, repeatable, catches regressions.
  • Online: measure live traffic: thumbs, escalations, task completion, latency, cost. Catches what your set does not cover.
  • You need both: offline to decide, online to discover.
Notes · 10.2 LLM-as-judge you can trust

Calibrate the judge before you believe it

Write a rubric a person could apply

  • Prefer binary or 3-level scores per criterion ("every claim is supported by the context: yes / no") over a vague 1 to 10.
  • Give the judge the question, the context, the answer and, when you have one, a reference.
  • Ask for a short reason before the score, and store it: reasons are how you debug the judge.

Known biases

  • Position: prefers the first (or second) answer shown.
  • Verbosity: prefers longer answers.
  • Self-preference: prefers outputs from its own model family.
  • Leniency: rates almost everything as good.

Measure agreement with humans

raw agreement p_o = share of items where judge = human chance p_e = p_judge·p_human + (1 - p_judge)(1 - p_human) Cohen's kappa κ = (p_o - p_e) / (1 - p_e) κ below 0.4 weak · 0.4 to 0.6 moderate · above 0.6 substantial

Raw agreement flatters a judge when most answers are good: always saying "good" can agree 90% of the time. Kappa removes the agreement you would get by chance.

Fix position bias

Run every pairwise comparison twice with the order swapped. Count a win only when both runs agree; treat disagreements as ties.

Code lab · 10.3 is the gain real?

Confidence intervals and paired comparisons

Moving from 78% to 82% on 200 items looks like progress. With that few items, it can easily be noise. Before you ship, put an interval around the difference.

standard error of an accuracy p on n items: SE = √(p(1 - p) / n) difference of two independent accuracies: SE_diff = √(p₁(1-p₁)/n + p₂(1-p₂)/n) 95% CI = (p₂ - p₁) ± 1.96 · SE_diff

If the interval includes 0, you have not shown an improvement. Halving the interval needs four times as many items.

Pair the comparison

  • Both versions run on the same items, so compare item by item: which ones did the new version fix, which did it break?
  • A paired bootstrap resamples items and recomputes the difference thousands of times; the middle 95% is the interval.
  • Pairing removes the noise from some items simply being harder than others, so it detects real gains with far fewer items.

Notes · 10.4 watching quality in production

Monitoring, drift and safe rollouts

Signals to collect on every request

  • Trace with spans for retrieval, each model call and each tool (Module 7.8).
  • Tokens, cost, latency (time to first token and total), errors, refusals.
  • User signals: thumbs, edits to the answer, escalation to a human, retries.
  • Sampled judge scores on live traffic (for example 2% of requests), checked weekly by a person.

Drift: when the inputs change

  • New topics or products appear, users phrase things differently, a source document changes.
  • Watch input length, language mix, retrieval scores, the share of "I do not know" answers and the embedding distribution of questions.
  • When a metric moves, pull examples and add the new cases to the offline set.
Practice · answer first, then open

Module 10 questions

  1. Your judge agrees with humans 92% of the time. Why might that still be useless?

    If 90% of answers are good, a judge that always says "good" agrees 90% of the time while catching no failures. Report Cohen's kappa and, more usefully, the judge's recall on the bad answers.

  2. How many eval items do you need?

    Enough that the confidence interval on the difference you care about excludes zero. At 80% accuracy, 200 items give an interval of roughly ±5.5 points on one accuracy, so a 2-point gain needs thousands of items or a paired design. Start with 100 well-chosen items and grow the set from production failures.

  3. Why compare versions item by item instead of only comparing totals?

    The same items run through both versions, so item difficulty cancels out. A paired test detects smaller real changes, and listing fixed and broken items shows exactly what changed, including regressions hidden inside a higher total.

  4. How do you stop a pairwise judge preferring whichever answer comes first?

    Run each comparison in both orders and count a win only when both runs agree; otherwise call it a tie. Also randomise order across items and track how often the judge's verdict flips.

  5. Offline scores improved but user complaints went up. What happened?

    The offline set no longer represents real traffic (drift), or the metric rewards something users do not value (for example longer answers). Sample the complaints, add them to the set, and check whether the judge or rubric is measuring the wrong thing.

  6. What is a shadow deployment for?

    Running a new version on real inputs without showing its outputs to users. You see real latency, cost and failure cases with zero user risk, and can compare its outputs with the current version's before any canary.

  7. Which production metrics would warn you of a broken retriever?

    Falling retrieval similarity scores, a rise in "I do not know" or refusal answers, fewer citations per answer, more user escalations, and lower sampled faithfulness scores.

Notes · 11.1 what a reasoning model does differently

Thinking before answering

How they are trained

  • Reinforcement learning with verifiable rewards (Module 6.5): math answers and unit tests check the result, so long chains that reach correct answers are reinforced.
  • Behaviours such as self-checking and trying another approach emerge because they raise the reward.
  • Accuracy on hard problems keeps rising as the model is allowed to think longer: "test-time compute scaling".

Notes + code · 11.2 more samples, better answers?

Self-consistency, best-of-n and verifiers

Three ways to spend compute at answer time

  • Self-consistency: sample n answers at non-zero temperature and take the most common final answer.
  • Best-of-n with a verifier: sample n, score each with a checker (unit tests, a math checker, a reward model) and keep the best.
  • Sequential revision: draft, critique, revise. Helps when a checker can point at the mistake.
n samples, each correct with probability p (independent): P(majority correct) = Σ over k > n/2 of C(n, k) · p^k · (1 - p)^(n-k) p = 0.6: n = 1 → 0.60, n = 5 → 0.68, n = 15 → 0.79
Sampling only amplifies

If a single sample is right less than half the time and its wrong answers agree with each other, majority voting makes things worse. Voting works when wrong answers are scattered and the right one is the most common. A real verifier beats voting whenever you have one.

Cost

n samples cost n times the tokens. Use it on hard, high-value requests, stop early once a clear majority appears, and compare against simply raising effort on one sample.

Notes + code · 11.3 constrained decoding

Making invalid output impossible

  • A JSON schema or regex is compiled into a finite-state machine (or a grammar parser) over the tokenizer's vocabulary.
  • Each step asks the state machine which tokens can come next, sets every other logit to −∞, and samples.
  • Libraries such as Outlines, XGrammar and llama.cpp grammars do this for open models; API providers do it behind "structured outputs" and strict tool schemas.
  • Constraints guarantee shape, not truth: still validate values (Module 3.8).
  • Very tight constraints can hurt quality if they force the model away from what it wanted to write; give fields room (for example a free-text "reasoning" field before the answer field).
  • The masking work is small next to the forward pass, so constrained decoding barely changes speed.

Notes · 11.4 prompting reasoning models

Describe the goal, not every step

Do

  • State the goal, the constraints and what a good answer looks like.
  • Give all the context up front; long agent tasks go better with the full brief at the start.
  • Ask for checks where they matter ("run the tests before answering").
  • Tune effort per route with evals; keep the cheapest setting that holds quality.

Avoid

  • Rigid step-by-step scripts written for older models; they can make answers worse.
  • "Think step by step" when the model already thinks; it adds nothing.
  • Judging latency only by the first visible token; thinking happens before it.
  • Setting the output limit too low: thinking tokens count toward it on many APIs.
Practice · answer first, then open

Module 11 questions

  1. What is test-time compute scaling?

    Improving answers by spending more computation at inference instead of training a bigger model: longer thinking, more samples with voting or a verifier, or revision loops. On hard reasoning tasks, accuracy keeps improving as this budget grows.

  2. When does self-consistency fail?

    When a single sample is usually wrong and its wrong answers tend to agree, majority voting locks in the wrong answer. It also cannot help on open-ended outputs with no comparable final answer.

  3. Best-of-n vs self-consistency?

    Self-consistency picks the most common answer and needs no checker. Best-of-n scores each candidate with a verifier and picks the best, so it can find a rare correct answer, but it needs a reliable verifier (tests, a math checker, a reward model).

  4. Why is a reasoning model a poor fit for high-volume classification?

    The thinking tokens add cost and latency to every request while simple labels gain little from long reasoning. A smaller model at low effort, or a fine-tuned classifier, is usually as accurate and much cheaper.

  5. How does constrained decoding guarantee valid JSON?

    The schema is compiled into a state machine. At each step every token that cannot legally come next is masked to probability zero, so the model can only produce a string the schema accepts.

  6. Your reasoning model's answers are often cut off. Why?

    The output token limit covers the thinking as well as the answer on many APIs, so a small limit runs out mid-answer. Raise the limit, lower the effort, or ask for a shorter answer.

Notes · 12.1 where inference time goes

Memory-bound decoding and the roofline

arithmetic intensity = FLOPs done / bytes moved decode, batch 1: each weight (2 bytes in bf16) is read once and used for ~2 FLOPs → ~1 FLOP per byte GPU balance point: compute / bandwidth e.g. ~990 TFLOPs / 3.35 TB/s ≈ 300 FLOPs per byte 1 ≪ 300, so decode waits on memory

Batching B sequences reuses each weight read B times, raising intensity about B-fold. That is why serving many users at once is almost free until the KV cache fills memory.

Notes + code · 12.2 PagedAttention and prefix sharing

Stop reserving memory you never use

  • Naive servers reserve a contiguous KV region for the maximum length of every request. Most requests stop far earlier, so most of that memory sits empty.
  • PagedAttention stores the KV cache in small fixed blocks (for example 16 tokens) and keeps a block table per request, like an operating system's page table.
  • Waste drops to at most one partly filled block per request, so many more requests fit in the same memory.
  • Requests that share a prefix (system prompt, documents) can point to the same blocks: prefix sharing, with copy-on-write when they diverge.

Notes + code · 12.3 quantization in practice

Scales, zero points and outliers

symmetric: q = round(x / s), s = max|x| / 127 asymmetric: q = round(x / s) + z, z shifts the range dequantize: x̂ = s · (q - z) granularity: per tensor → per channel / row → per group of 64 or 128
  • Finer granularity means more scales to store but much smaller errors.
  • Weight-only int8 / int4 (GPTQ, AWQ) cuts bytes read per token, which is what memory-bound decode needs.
  • Weights and activations (W8A8, FP8) also speed up the matrix multiplies, which matters for prefill and large batches.
Outliers

A few weights or activation channels are far larger than the rest. One shared scale stretched to fit them rounds most small values to zero. Fixes: per-channel or group scales, keeping outlier channels in higher precision, or moving the difficulty from activations to weights (the SmoothQuant idea), and choosing scales from calibration data (AWQ, GPTQ).

Always re-run your evals after quantizing: average quality often holds while rare, hard cases degrade.

Notes · 12.4 speculative decoding and distillation

Fewer expensive steps, or a cheaper model

Speculative decoding, with costs

acceptance rate α, draft length k, draft cost c (c = one draft step's cost relative to one target step) tokens per target step E = (1 - α^(k+1)) / (1 - α) cost per target step k·c + 1 speedup E / (k·c + 1) α = 0.8, k = 4, c = 0.05 → 3.36 / 1.2 ≈ 2.8×
  • Helps most at low batch sizes, where the target is memory-bound and verifying k tokens costs about the same as generating one.
  • At large batches the GPU is already busy, so gains shrink.

Distillation

  • Train a small student on a large teacher's outputs or probabilities (Module 6.5).
  • For one narrow task, a distilled small model can match the large model at a fraction of the cost and latency.
  • The student is only as good as the data: generate varied inputs, filter teacher outputs with your evals, and keep a fallback to the large model for hard cases.

Practice · answer first, then open

Module 12 questions

  1. Why is decoding memory-bound while prefill is compute-bound?

    Prefill processes many prompt tokens per weight read, so each byte of weights is used for many FLOPs. Decoding one token per sequence reads every weight for only a couple of FLOPs, so the GPU waits on memory bandwidth.

  2. How does batching make decoding cheaper per token?

    All sequences in a batch share one read of the weights, so cost per token falls roughly in proportion to batch size until compute becomes the limit or the KV cache fills memory.

  3. What problem does PagedAttention solve?

    Memory wasted by reserving a contiguous maximum-length KV region per request. Fixed-size blocks allocated on demand waste at most one partial block per request and allow sharing of common prefixes.

  4. Why can one outlier ruin per-tensor int8 quantization?

    The single scale is set by the largest value, so the step size becomes huge and most small values round to zero. Per-channel or group-wise scales, or keeping outliers in higher precision, contain the damage.

  5. Speculative decoding gives a 2.5× speedup on your laptop but little on your busy server. Why?

    At batch 1 the target model is memory-bound, so verifying several drafted tokens is nearly free. On a busy server large batches already keep the GPU compute-bound, so the extra verification work is not free and the gain shrinks.

  6. Your bill doubled. What do you try first?

    Measure where tokens go (input vs output, per route), turn on or fix prompt caching, trim retrieved context and output length, and route easy requests to a smaller model or lower effort. Quantization, speculative decoding and distillation come later because they cost more to build and maintain.

  7. When is distillation the right call?

    When one narrow, high-volume task dominates cost or latency, you have evals to prove the student matches the teacher, and you can keep a fallback to the large model for the hard cases.
