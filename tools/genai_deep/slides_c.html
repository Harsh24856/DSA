Deep dive · 5.10 LangChain core

Runnables and LCEL: how LangChain pieces snap together

LangChain is a set of standard interfaces (chat models, prompts, retrievers, tools, output parsers) with integrations for hundreds of providers. Every piece is a Runnable, so every piece has the same methods, and pieces compose with | (the LangChain Expression Language, LCEL).

The Runnable interface

MethodWhat you get
invoke / ainvokeone input → one output (sync / async)
batchmany inputs in parallel, with a concurrency limit
stream / astreamoutput chunks as they are produced
astream_eventsevery inner step (retriever done, token produced) for UIs
with_retry / with_fallbacksretry on errors, or fall back to another model

Composition rules

  • a | b: run a, feed its output to b (RunnableSequence).
  • A dict or RunnableParallel: run branches on the same input, collect a dict.
  • A plain function in a chain becomes a RunnableLambda.
  • RunnablePassthrough: pass the input through unchanged; .assign(k=...) adds a key.
  • model.with_structured_output(PydanticModel): the model returns a validated object instead of text.
When to use LCEL

Straight pipelines (prompt → model → parser, simple RAG). As soon as you need loops, branching on results or memory across turns, use LangGraph; its nodes can still call LCEL chains.

Check yourself

  1. What does the dict at the start of the chain receive and return?

    It receives the raw question. Each branch runs on that same input: the retriever branch returns formatted context, the passthrough returns the question. The result is {"context": ..., "question": ...}, exactly the variables the prompt template needs.

  2. Why does streaming work through the whole chain?

    Every Runnable implements stream. Components that can pass chunks along (the model, the string parser) do so as soon as chunks arrive; components that need the whole input (the retriever) run first and then hand over.

Deep dive · 5.11 agents in LangChain 1.x

create_agent, middleware and streaming

In LangChain 1.x, create_agent is the standard tool-calling agent. Under the hood it builds a LangGraph graph: a model node and a tools node in a loop. Middleware hooks into that loop to change behaviour without rewriting it. (Older code uses langgraph.prebuilt.create_react_agent; the idea is the same.)

Middleware you will actually use

  • SummarizationMiddleware: compress old turns when the context gets long.
  • HumanInTheLoopMiddleware: pause before chosen tools for approval (uses LangGraph interrupts).
  • ModelCallLimitMiddleware / tool call limits: stop runaway loops and cost spikes.
  • ModelFallbackMiddleware: switch to another model when one fails.
  • PIIMiddleware: detect and redact personal data in inputs and outputs.
  • Custom: subclass AgentMiddleware and implement only the hooks you need.

Streaming modes (LangGraph underneath)

stream_modeEach chunk is
updateswhat one node just changed
valuesthe full state after each step
messagesLLM tokens as they are generated, with metadata
customanything your node writes (progress, logs)

UIs usually combine messages (typing effect) with updates (show "searching the docs...").

Check yourself

  1. The agent ran but used the tool 40 times. Which guards belong in every agent?

    A model or tool call limit, a timeout, a cost budget per request, and tracing (LangSmith or similar) so you can see why it looped. Often the root cause is a tool returning an unclear error the model keeps retrying.

  2. create_agent or a hand-built StateGraph?

    create_agent for the standard "model plus tools in a loop", with middleware for most customisation. A hand-built graph when the flow itself is custom: fixed steps, parallel branches, several agents, or approval stages that are not about a single tool call.

How to choose

What transfers between all of them

  • The loop is always: model → tool calls → results → model, until done.
  • Tools are functions with a name, description and JSON schema; MCP lets one tool server work in all of them.
  • State, memory, guardrails, tracing and evals are separate concerns, whatever the framework calls them.
  • APIs in this space change quickly. Pin versions, read the changelog when upgrading, and keep your business logic in plain functions the framework calls.

Check yourself

  1. What is the difference between LangChain and LangGraph in one sentence?

    LangChain gives you the components (models, prompts, retrievers, tools) and a standard agent; LangGraph gives you the runtime that wires steps into a stateful, resumable graph, and LangChain's agents run on it.

  2. Why can DSPy improve a pipeline without you editing prompts?

    You declare what each step takes and returns, plus a metric. Its optimisers try instructions and few-shot examples, measure the metric on your data, and keep what scores best, much like training weights but for prompts.
